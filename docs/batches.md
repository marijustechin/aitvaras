# Receiving: deliveries, batches and packages (Gavimai, partijos ir pakuotės)

> Status: **implemented** — incoming **deliveries** (`Gavimai`, ATV-042) above
> bag-by-bag receiving (ATV-029), formal GoodsReceipt reconciliation (ATV-030),
> physical handling-unit correction/void (ATV-041) and packaging/tare master data
> (`Tara`, ATV-043). One physical arrival of one supplier on one arrival date
> contains one or more resource **batches**, each going to one warehouse and
> containing individual physical **packages** received by **weight** (gross −
> tare = net), with a unique barcode, documentary confirmation and an auditable
> correction trail. This is a slice of the confirmed inventory/production
> direction (see [scope.md](scope.md)); it deliberately does **not** implement
> stock balances, movements, production lineage or costing.

## What a Gavimas (incoming delivery) is

A **Gavimas** (`IncomingDelivery`) is one physical incoming **arrival**: the goods
of **one** supplier on **one** arrival date. It is created by a warehouse worker at
the start of receiving and is the **user-facing receiving unit**. It carries a
compact human-facing code `GYYMM-NN` (e.g. `G2609-01`), generated by the system,
monthly-sequenced and unique; the code encodes no business data.

One delivery may contain **several resources**, and different resources from the
same delivery may go to **different warehouses**. The delivery is the container
**above** batches. Only supplier + arrival date are owned by the delivery. **No
transport/vehicle entity exists** — the truck/vehicle is **outside system scope**
and must not be modelled.

## What a Partija (batch) is (and is not)

A **Partija** is the **internal** grouping of **one resource** into **one
warehouse** inside a single delivery. A delivery therefore contains one batch per
`(resource, warehouse)` combination; the same resource into two warehouses is two
batches. It stays **`PENDING`** until a responsible person (Eimantas) formally
confirms it against a `Pajamavimas` (GoodsReceipt). The batch has its own compact,
**delivery-local** `code` (`P01`..`P99`) that is secondary to the human-facing
delivery code and is not printed on labels.

Warehouse workers record the **physical truth** (individual packages and their
measured weights); the formal/documentary **confirmation** records the accepted
documentary weight, acquisition value, an optional **piece count** and the link
to the formal document. The formal GoodsReceipt is reconciled with the batch
**without duplicating quantities**: the packages are the physical quantity source,
the receipt is the documentary/financial record, and the two are joined by
`Batch.receiptLineId` (see "Reconciliation").

A delivery/batch is **not** stock: creating them, a package or a reconciliation
does **not** change any balance, and there is no quantity-on-hand anywhere in the
system.

## What a package (user-facing `Pakuotė`; internal `Bag`) is

The user-facing term is **`Pakuotė`** (a package — bag, box, pallet, other); the
internal model/API/module name is still `Bag` (`Maišas` was too bag-specific as a
user-facing term). A **`Pakuotė`** is one physical **package** inside exactly one
batch. Incoming raw material usually arrives as many packages of one batch, and
**packages of the same batch may have different weights**.

Physical receiving is **always by actual weight**. Every package references one
packaging/tare type (**`Tara`**, see [packaging-types.md](packaging-types.md)) and
stores the entered `grossWeight` plus the server-derived
`netWeight = grossWeight − tareWeightKg`; gross and tare are preserved for
traceability. There is **no KG/PCS unit selector** and no count-based physical
receiving mode — even goods that are conceptually counted in pieces are physically
received by weight. A package is not deleted: an erroneous package is corrected or
voided (see "Physical correction and voiding").

Every package is **placed in a warehouse location** that belongs to the batch's
warehouse; the location is required, and may differ per package.

Each package receives its own **unique barcode** (`Brūkšninis kodas`), rendered as
a scannable EAN-13 graphic on the label. The barcode identifies the **physical
package only** and encodes **no business data** (no supplier, delivery, resource,
date or batch) — the relationships provide the meaning.

When registering the next package of a batch, the form **preselects the location
of the most recently registered package** (`suggestedLocationId`, derived from the
persisted data, so it survives refreshes and works across workstations); the
worker may still change it. With no previous package, no location is preselected
(there is no arbitrary fallback).

## Documentary piece count

Reconciliation may store an optional **documentary piece count**
(`Batch.documentPieces`, a positive integer or `null`). It is **additional
business/documentary information** entered by the ADMIN (e.g. `document pieces:
500` alongside `document weight: 188.000 kg` and a measured `186.400 kg`). It is
**not** a physical receiving unit, it does **not** replace the document weight, it
does **not** replace the measured physical weight, and it does **not** drive any
package or batch total. There is no per-package piece allocation.

## Domain model

```text
IncomingDelivery (Gavimas)
├── id
├── code                (unique, human-facing; GYYMM-NN; system-generated)
├── supplierId          (Tiekėjas — active SUPPLIER partner)
├── arrivalDate         (physical arrival; independent of createdAt)
├── createdById
├── createdAt / updatedAt
└── batches[]
    (no warehouse here — a delivery spans warehouses; no vehicle)

Batch (internal grouping)
├── id
├── code                (delivery-local, unique per delivery; P01..P99)
├── deliveryId          (owning Gavimas)
├── resourceId          (Išteklius)
├── warehouseId         (Sandėlis — the batch's warehouse)
├── status              PENDING | CONFIRMED  (default PENDING)
├── receiptLineId       (nullable, unique — formal GoodsReceipt line link)
├── documentWeight      Decimal(14,3)? — accepted documentary weight
├── documentPieces      Int? — optional documentary piece count (positive)
├── acquisitionAmount   Decimal(14,2)? — accepted acquisition value (EUR)
├── confirmedAt         (set only on a clean CONFIRMED result)
├── createdById
├── createdAt / updatedAt
├── @@unique(deliveryId, resourceId, warehouseId)
└── bags[]              (derived totals only — not stored)

Bag (physical package)
├── id
├── barcode             (unique; opaque physical-package identifier)
├── batchId
├── packagingTypeId     (Tara; required; ON DELETE RESTRICT)
├── grossWeight         Decimal(14,3); the value the worker enters
├── tareWeightKg        Decimal(14,3); immutable/current snapshot of the tare used
├── netWeight           Decimal(14,3) = grossWeight − tareWeightKg (snapshot)
├── status              ACTIVE | VOIDED (default ACTIVE; never deleted)
├── warehouseLocationId (required; must belong to the batch's warehouse)
├── voidedById          nullable — who voided the package
├── voidedAt            nullable — when it was voided
├── voidReason          nullable varchar(500) — optional free-text reason
├── createdById
└── createdAt / updatedAt

PackagingType (Tara)
├── id
├── name                (unique)
├── tareWeightKg        Decimal(14,3); never floating point; 0 allowed
├── active              (deactivated, never deleted)
└── createdAt / updatedAt

BagCorrection (append-only audit trail)
├── id
├── bagId
├── kind                PACKAGING | GROSS_WEIGHT | LOCATION | VOID
├── previousValue       nullable varchar(255) — e.g. old value / name
├── newValue            nullable varchar(255) — e.g. new value / name
├── reason              nullable varchar(500)
├── createdById
└── createdAt
```

Derived values shown in the API/UI (never stored, never client-supplied):

- `bagCount` — number of **active** packages in the batch (voided ones excluded);
- `totalNetWeight` — sum of **active** package **net** weights (the **measured**
  quantity), serialised as a **decimal string**; voided packages are excluded;
  gross and tare are preserved per package for traceability;
- `difference` — `documentWeight − totalNetWeight` for a reconciled batch (same
  precision; a signed decimal string), or `null` before reconciliation;
- `suggestedLocationId` — the location of the most recent package (batch detail
  only), used to preselect the next package's location.

Weights are persisted as PostgreSQL `numeric` (Prisma `Decimal`) and exchanged as
**strings**, so they never pass through JavaScript floating point. The documentary
weight is **never** written over the measured weight.

## Delivery code, batch code and package barcode

- **Delivery code** — `G<YY><MM>-<NN>`, e.g. `G2609-01`. Generated by the API
  (two-digit sequence within the calendar month, resetting each month, max `99`
  with `DELIVERY_CODE_EXHAUSTED` past that), unique via a database constraint with
  retry on conflict. It is the **human-facing** reference shown in the receiving
  UI and printed on labels, and encodes no business data.
- **Batch code** — `P<NN>`, e.g. `P01`. Compact and **local to its delivery** (the
  first batch in a delivery is `P01`, the second `P02`, ..., max `P99`; the sequence
  resets for each new delivery and never silently produces `P100` —
  `BATCH_CODE_EXHAUSTED` past `P99`). Generated by the API, unique per delivery via
  a database constraint on `(deliveryId, code)` with retry on conflict. It is
  **secondary** to the delivery code and is not printed on labels. The
  IncomingDelivery code is the **main human-facing receipt identifier**; together
  they read e.g. `G2610-01 / P01`.
- **Package barcode** — a 13-digit, **EAN-13-shaped** code (GS1 `20` restricted-
  circulation prefix + 10 random digits + a valid check digit). Generated by the
  API, unique via a database constraint with retry on conflict. It encodes no
  business data and is **not** copied to child packages (splitting is out of scope).

## Status

| Key | Lithuanian | Meaning |
|---|---|---|
| `PENDING` | Laukiama patvirtinimo | created; packages may still be added |
| `CONFIRMED` | Patvirtinta | formally confirmed (terminal) |

There is **no** `DISCREPANCY` batch status. A documentary/physical mismatch does
**not** block confirmation: the batch is `CONFIRMED` and the mismatch is recorded
as a separate, long-lived `ReceivingDiscrepancy` (see "Receiving discrepancy").
Packages may be added, corrected or voided **only** while `PENDING`; a `CONFIRMED`
batch is frozen.

## Reconciliation (formal confirmation)

Reconciliation is the documentary/financial act performed later by an `ADMIN`
(Eimantas), after the physical packages have been registered. It records the
accepted documentary values, confirms the batch and resolves/creates the internal
formal-document anchor **server-side** — the user never selects a `GoodsReceipt`
or `GoodsReceiptLine`. It creates **no** packages and no stock.

- **Confirmation is never blocked by a mismatch.** An exact match
  (`measuredWeight == documentWeight`) confirms directly with no discrepancy. A
  mismatch still confirms, but the client must explicitly send
  `acknowledgeDiscrepancy: true` (`DISCREPANCY_NOT_ACKNOWLEDGED` otherwise); the
  document weight is **not** required to be edited to match the physical weight.
- **Two separate quantities:** the **measured** weight is always the server-derived
  `SUM(bags.netWeight)` over the batch's active packages; the **documentary**
  weight (`documentWeight`) is entered at reconciliation. They are never merged,
  and the signed `difference = measuredWeight − documentWeight` (positive =
  physically received **more** than documented) is shown as-is (no tolerance).
  `documentPieces` is optional and independent.
- **Acquisition value:** `acquisitionAmount` (EUR) is stored on the batch as its
  **initial acquisition value**.
- **Relationship:** `GoodsReceipt → GoodsReceiptLine → Batch → Bags`.
  `Batch.receiptLineId` is a nullable, **unique** foreign key, so one receipt line
  reconciles at most one batch and one batch is reconciled to at most one line; a
  receipt may still contain multiple lines/resources/batches. The relationship is
  internal plumbing; the client sends only formal data.
- **Internal anchor resolution (no technical selector):**
  `POST /batches/:id/reconcile` carries only formal data (`documentWeight`,
  `acquisitionAmount`, optional `documentPieces`, optional document date/number).
  The server resolves the `GoodsReceiptLine` anchor deterministically:
  1. reuse the line the batch is already linked to (retry — no duplicate);
  2. reuse an existing compatible, **unlinked** receipt line (same supplier via
     the receipt partner, resource and warehouse);
  3. otherwise create a `GoodsReceipt` with one line from the batch + formal data
     (unit `KG`, quantity = documentary weight, unit price = value ÷ weight).
  A reused line is never mutated; the accepted documentary values live on the
  batch. Retrying never duplicates a receipt or line.
- **Document metadata:** `documentDate`/`documentNumber` live on the `GoodsReceipt`
  and may be supplied at reconciliation when not already set; an existing value is
  never overwritten.
- **Transactional & idempotent:** the confirm update and the discrepancy creation
  happen in one transaction; the batch update is conditional on not being
  `CONFIRMED`, so a retry (or concurrent confirmation) cannot create a duplicate
  discrepancy.

### Reconciliation error codes

| Code | HTTP | Meaning |
|---|---|---|
| `BATCH_NOT_FOUND` | 404 | unknown batch |
| `BATCH_EMPTY` | 400 | batch has no packages |
| `BATCH_ALREADY_CONFIRMED` | 409 | batch is already `CONFIRMED` |
| `DISCREPANCY_NOT_ACKNOWLEDGED` | 400 | mismatch not explicitly acknowledged |
| `RECEIPT_CREATE_FAILED` | 409 | internal receipt creation failed (unexpected) |

## Receiving discrepancy (neatitikimas)

When a batch is confirmed with a non-zero `measuredWeight − documentWeight`, the
server records a `ReceivingDiscrepancy` (created by
`POST /batches/:id/reconcile` with `acknowledgeDiscrepancy: true`):

- `batchId` (**unique** — one discrepancy per confirmed batch), `supplierId`
  (snapshot from the delivery), `measuredWeight`, `documentWeight`,
  `differenceWeight` (signed `measured − document`), `status`, `createdById`,
  `createdAt`, `settledAt?`.

The discrepancy lifecycle is **separate** from the confirmation lifecycle:

- the batch is already `CONFIRMED`; the physical stock remains the measured net
  weight (gross/tare preserved per package);
- the discrepancy may stay **open for a long time**;
- it is settled later **by additional physical weight or by money/credit** through
  the append-only `DiscrepancySettlement` ledger (`WEIGHT`/`MONEY`); **no
  money↔weight conversion is ever performed**. Statuses:
  `OPEN | PARTIALLY_SETTLED | SETTLED`, with `settledAt` set once fully covered.

In the `Gavimai` queue a confirmed batch with an unresolved discrepancy is shown as
`Patvirtinta` with a `Neatitikimas` marker (it is **not** under `Reikia
patvirtinti`); the ADMIN detail shows the signed difference and the batch's
discrepancy records.

The discrepancy register and its settlement ledger are documented in full in
[discrepancies.md](discrepancies.md) (ADMIN `Ataskaitos → Neatitikimai`).

## Physical correction and voiding (worker)

Physical reality is authoritative. A warehouse worker may correct what they
physically measure/place without an ADMIN, while the batch is not yet `CONFIRMED`:

- **Correct a package** (`PATCH /batches/:id/bags/:bagId`): change
  `packagingTypeId`, `grossWeight` and/or `warehouseLocationId` on an **active**
  package. At least one field is required; the package must still be `ACTIVE` and
  the batch not `CONFIRMED`. A changed packaging type re-snapshots
  `Bag.tareWeightKg` from the selected type; a changed packaging type or gross
  weight recomputes `netWeight` server-side (`grossWeight − tareWeightKg`). The new
  location must exist, be active and belong to the batch's warehouse. Only the
  **changes** are recorded, one `BagCorrection` row per changed field
  (`PACKAGING` — with previous/new packaging name **and tare**, `GROSS_WEIGHT`,
  `LOCATION`); a no-op records nothing.
- **Void a package** (`POST /batches/:id/bags/:bagId/void`): the package is
  **never deleted**. It is marked `VOIDED` (who/when and optional reason) and
  excluded from the measured weight and active count; its barcode and history are
  preserved. A `VOID` row is appended to the trail.

The correction trail (`BatchDetail.corrections`, newest first) records the kind,
the affected package's barcode, previous/new value, reason, who and when.

### Correction error codes

| Code | HTTP | Meaning |
|---|---|---|
| `BAG_NOT_FOUND` | 404 | unknown package within the batch |
| `BATCH_CONFIRMED` | 409 | batch is `CONFIRMED` (frozen) |
| `BAG_VOIDED` | 400 | package is already `VOIDED` |
| `PACKAGING_INACTIVE` | 400 | selected packaging type is inactive |
| `GROSS_NOT_ABOVE_TARE` | 400 | gross weight is not greater than the tare |

- **`Gavimai`** (`/receipts`) is the ADMIN received-batch **queue** (status /
  supplier / resource / warehouse / arrival-date / code filters; default `Reikia
  patvirtinti` = the not-yet-confirmed `PENDING` batches) and
  `/receipts/batches/[id]` is the **ADMIN review** screen (batch context,
  read-only package list, label preview/print, formal reconciliation form). The
  default queue is **not date-bounded**: the `Priėmimo data` filters start empty
  so old pending items are never silently hidden (the generic supplier/resource/
  warehouse options read `Visi`). Each
  queue row is a **whole-row link**. Queue columns: `Gavimas`, `Partija`,
  `Priėmimo data`, `Tiekėjas`, `Išteklius`, `Sandėlis`, `Pakuotės / kiekis`,
  `Būsena` — status is neutral for `PENDING` and emerald for `CONFIRMED`; a
  confirmed batch with an unresolved discrepancy also carries a `Neatitikimas`
  marker. The filter panel has an **`Atstatyti filtrus`** action that clears every
  filter back to the default view. ADMIN does **not** create receiving records
  here.
- The batch detail page shows the batch context and a **read-only** list of the
  registered packages (`Barkodas`, `Vieta`, `Neto svoris`, `Būsena`,
  `Užregistruota`) with an optional label preview/reprint; voided packages are
  shown muted. It also
  shows the **`Pataisymų istorija`** (correction history) table. There are **no**
  package-creation or correction controls here (those are worker actions).
- For a non-confirmed batch, `ADMIN` sees a **reconciliation form** with formal
  data only — `Dokumentinis svoris`, `Dokumentiniai vienetai` (optional),
  `Įsigijimo vertė`, `Dokumento data`, `Dokumento Nr.` — plus the `Faktiškai
  susverta` / `Dokumentuose` / `Skirtumas` summary and the **`Patvirtinti gavimą`**
  action. A `CONFIRMED` batch shows a read-only summary. The detail page's back
  link returns to the `Gavimai` queue (`/receipts`).

### Warehouse-worker receiving UI (`Registruoti sandėlyje`)

The warehouse worker's job is the **physical** receiving step only; the formal
`Pajamavimas` process is administrative and is not part of their flow.

- **Home** (`/`): for a receiving role the home is a focused operational
  workplace whose primary action is the prominent `Registruoti sandėlyje` button.
- **Receiving list** (`/receiving`, protected by the receiving roles): the open
  receiving queue **`Nepatvirtinti gavimai`** plus the `Naujas gavimas` action.
  The queue is **derived from the child batches** (there is **no** stored delivery
  status): a delivery is listed while it has at least one `PENDING` batch — or no
  batches yet (just created); a delivery whose batches are **all `CONFIRMED`**
  disappears. Confirmed history stays in the ADMIN `Gavimai` workflow, not here.
- **Delivery screen** (`/receiving/[deliveryId]`): selecting an existing delivery
  (or creating one) navigates to its own route, so the URL is
  bookmarkable/refreshable and browser Back works naturally; a secondary
  `← Gavimų sąrašas` action returns to the list, and the top-level
  `Registruoti sandėlyje` navigation always lands on the list (never on a
  resilient-only selection). The screen is **delivery first**: `Naujas gavimas`
  opens the delivery header (**`Tiekėjas`** + **`Atvykimo data`** only; no
  warehouse, no resource; the code is system-generated) with the primary action
  `Pradėti gavimą`. Inside a delivery the header shows `Gavimas <code>`, supplier
  and arrival; a compact `Gavimo turinys` table lists the batches already
  registered (resource, **warehouse**, active package count, total weight,
  status). The worker then uses **`Registruojama rūšis`** (`Išteklius` +
  `Sandėlis` + `Pradėti registruoti`) to start or resolve one batch per
  resource/warehouse. **`Kitas išteklius`** clears the active resource/batch and
  starts another batch **in the same delivery** (packaging preference is
  batch-specific — a new batch starts without a `Tara` selection). Package entry
  takes **`Tara`** (active packaging types only), **`Vieta`** (required) and
  **`Bruto svoris`**; the UI shows the calculated **`Taros svoris`** and **`Neto
  svoris`** (the worker enters only the gross weight). The batch's **latest active
  package** supplies the suggested packaging type (`suggestedPackagingTypeId`) and
  location (`suggestedLocationId`) — server-derived so they survive a
  refresh/re-entry; a batch with no active package suggests nothing.
- **Save actions:** **`Išsaugoti ir spausdinti`** (primary — persists the package
  and goes **straight to the label surface**, invoking the browser print preview)
  and **`Išsaugoti`** (secondary — persists and returns to the form). Both keep the
  active resource/batch, the selected `Tara` and the last-used location
  (server-derived suggestions) and reset **only the gross weight**; closing the
  label returns to the same form. A failed save opens no label and keeps the
  entered data.
- **Package list:** below the entry form, the active batch's **active** packages
  are listed under `Partijos pakuotės`, newest first, with `Barkodas`, `Vieta`,
  `Neto svoris`, `Užregistruota` and row actions `Taisyti`, `Anuliuoti` and
  `Spausdinti` (reprint). Voided packages move to `Anuliuotos pakuotės`. Correcting
  a package opens an editor with `Tara`, `Vieta`, `Bruto svoris` and the computed
  tare/net.
- **Label:** `Gavimas: GYYMM-NN` (prominent), warehouse, location, category,
  resource, **`Neto svoris`** (primary; gross/tare shown as secondary
  traceability), and the barcode (value + scannable EAN-13 graphic). The internal
  batch code is not printed.
- **Navigation**: the worker navigates `Pradžia`, reference data under the
  `Žinynai` group (`Partneriai`, `Ištekliai`, `Sandėliai`) and
  `Registruoti sandėlyje`; the formal `Gavimai` queue and the administrative
  `Ataskaitos`/`Sistema` groups are hidden. `ADMIN` keeps full access. Server-side
  authorization is unchanged.

### Server-side validation (authoritative)

The API verifies (never trusting UI filtering):

- on delivery creation: the supplier exists, is active and holds the `SUPPLIER`
  role;
- on batch resolution: the delivery exists, and the resource and warehouse exist
  and are active;
- a package's `grossWeight` > 0, the selected packaging type exists and is active
  (`PACKAGING_INACTIVE` otherwise), and `grossWeight > tareWeightKg`
  (`GROSS_NOT_ABOVE_TARE` otherwise); the net weight is computed server-side and
  never trusted from the client;
- a package's **location is required** and must exist, be active and belong to the
  **batch's** warehouse (friendly message: `Pasirinkite sandėlio vietą.`);
- packages can be added or corrected **only** while the batch is `PENDING` (a
  `CONFIRMED` batch is frozen — `BATCH_CONFIRMED`); a corrected package must be
  `ACTIVE` (`BAG_VOIDED` otherwise);
- reconciliation requires a non-empty batch, a non-`CONFIRMED` batch, a compatible
  receipt line, `documentWeight > 0`, an optional positive-integer
  `documentPieces`, a non-negative acquisition amount, and — when the measured net
  weight differs from `documentWeight` — `acknowledgeDiscrepancy: true`; the
  measured weight and the signed difference are computed server-side and never
  trusted from the client.

## Referential behaviour

Deliveries reference `BusinessPartner` and `User`; batches reference
`IncomingDelivery`, `Resource`, `Warehouse`, `User` and (optionally) a
`GoodsReceiptLine`; packages reference `Batch`, `PackagingType`,
`WarehouseLocation` and `User`; `BagCorrection` rows reference `Bag` and `User`.
Referenced master data is
deactivated, never deleted, and foreign keys **restrict** deletion. There is no
delivery/batch/package delete endpoint — a package is **voided**, never deleted.

## Migration notes (historical data)

The `incoming_deliveries` migration (ATV-042) created **one delivery per existing
batch**, because the real shared arrivals of the past cannot be proven from stored
data. Each migrated delivery reuses its batch's id, copies the supplier + arrival
date and receives a deterministic per-month `GYYMM-NN` code; the batch **keeps its
warehouse**. Existing packages were preserved: `bags.quantity` was renamed to
`bags.weight` (the KG/PCS unit column was dropped) and `batches.document_pieces`
was added. Do not infer historical delivery grouping.

The `packaging_types` migration (ATV-043, extended by ATV-044) introduced
`PackagingType` and gross/net weights plus the `Bag.tareWeightKg` snapshot.
Existing handling units had **no known packaging/tare provenance**, so they were
attached to a dedicated, **inactive** `Nežinoma tara` row with tare `0.000`; their
tare **snapshot** is `0.000`, `grossWeight` was set equal to the stored weight and
`netWeight = grossWeight` is preserved unchanged (no invented tare). The inactive
row cannot be chosen for new receiving. New packages snapshot the selected
PackagingType's current tare.

The `batch_delivery_local_code` migration (ATV-047) shortened the human-facing
batch code to the delivery-local `P01`..`P99` and replaced the global unique
`batches.code` index with a composite unique index on `(deliveryId, code)`.
Existing batches were renumbered deterministically within each delivery (`P01`,
`P02`, ... by creation order, relationships preserved). **Limitation:** a delivery
with more than 99 historical batches would produce `P100+`; this cannot occur with
the current data (each migrated delivery holds a single batch) and new batches are
capped at `P99`.

## Open / not implemented

- **Vehicle/transport** — explicitly **outside system scope** (not modelled).
- **Historical delivery grouping** — migrated deliveries are one-per-batch.
- **Bag split / merge and EAN lineage to child packages** — not modelled.
- **Post-confirmation corrections** — a `CONFIRMED` batch is frozen.
- **Piece allocation per package** — not modelled; pieces are documentary only.
- **Packaging-type deletion** — never hard-deleted; deactivated only
  (`docs/packaging-types.md`).
- **Tolerance percentages** — exact equality is the only clean-confirmation rule.
- **`Bag`/`Maišas` naming** — the internal model is still called `Bag`; renaming
  it to `HandlingUnit` is a deferred, purely mechanical refactor.
- **VAT/accounting engine, cost redistribution, production transformations,
  output lots, order allocation** — confirmed future direction, not modelled here.
