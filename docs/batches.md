# Receiving: deliveries, batches and packages (Priėmimas, partijos ir pakuotės)

> Status: **implemented** — incoming **deliveries** (`Priėmimas`, ATV-042) above
> bag-by-bag receiving (ATV-029), formal GoodsReceipt reconciliation (ATV-030),
> physical handling-unit correction/void (ATV-041) and packaging/tare master data
> (`Tara`, ATV-043). One physical arrival of one supplier on one arrival date
> contains one or more resource **batches**, each going to one warehouse and
> containing individual physical **packages** received by **weight** (gross −
> tare = net), with a unique barcode, documentary confirmation and an auditable
> correction trail. This is a slice of the confirmed inventory/production
> direction (see [scope.md](scope.md)); it deliberately does **not** implement
> stock balances, movements, production lineage or costing.

## What a Priėmimas (incoming delivery) is

A **Priėmimas** (`IncomingDelivery`) is one physical incoming **arrival**: the goods
of **one** supplier on **one** arrival date. It is created by a warehouse worker at
the start of receiving and is the **user-facing receiving unit**. It carries a
compact human-facing code `GYYMM-NN` (e.g. `G2609-01`), generated by the system,
monthly-sequenced and unique; the code encodes no business data.

One delivery may contain **several resources**, and different resources from the
same delivery may go to **different warehouses**. The delivery is the container
**above** batches. Only supplier + arrival date are owned by the delivery. **No
transport/vehicle entity exists** — the truck/vehicle is **outside system scope**
and must not be modelled.

## What a Partija (batch) is (and is not)

A **Partija** is the **internal** grouping inside a single delivery and has a
**receiving mode** (`BatchReceivingMode`, `Svorinė`/`Vienetinė`):

- a **`WEIGHT`** (Svorinė) batch groups **one resource** into **one warehouse**; a
  delivery contains one batch per `(resource, warehouse)` combination, and the
  same resource into two warehouses is two batches;
- a **`PIECE`** (Vienetinė) batch groups **several product/resource item lines**
  (integer quantities) into **one warehouse** and owns **no** batch-level resource
  (the batch is the cost/provenance pool). See [piece-batches.md](piece-batches.md).

A batch stays **`PENDING`** until a responsible person (Eimantas) formally
confirms it. It has its own compact, **delivery-local** `code` (`P01`..`P99`)
that is secondary to the human-facing delivery code and is not printed on labels.

Warehouse workers record the **physical truth** (individual packages and their
measured weights); the formal/documentary **confirmation** records the
type-specific documentary quantity (weight in kg for WEIGHT, aggregate pieces in
`vnt.` for PIECE), the acquisition value and the link to the formal document. The
formal GoodsReceipt is reconciled with the batch **without duplicating
quantities**: the packages/item lines are the physical quantity source, the
receipt is the documentary/financial record, and the two are joined by
`Batch.receiptLineId` (see "Reconciliation").

A delivery/batch is **not** stock: creating them, a package or a reconciliation
does **not** change any balance, and there is no quantity-on-hand anywhere in the
system.

## What a package (user-facing `Pakuotė`; internal `Bag`) is

The user-facing term is **`Pakuotė`** (a package — bag, box, pallet, other); the
internal model/API/module name is still `Bag` (`Maišas` was too bag-specific as a
user-facing term). A **`Pakuotė`** is one physical **package** inside exactly one
batch. Incoming raw material usually arrives as many packages of one batch, and
**packages of the same batch may have different weights**.

Physical receiving is **always by actual weight**. Every package references one
packaging/tare type (**`Tara`**, see [packaging-types.md](packaging-types.md)) and
stores the entered `grossWeight` plus the server-derived
`netWeight = grossWeight − tareWeightKg`; gross and tare are preserved for
traceability. There is **no KG/PCS unit selector** and no count-based physical
receiving mode — even goods that are conceptually counted in pieces are physically
received by weight. A package is not deleted: an erroneous package is corrected or
voided (see "Physical correction and voiding").

Every package is **placed in a warehouse location** that belongs to the batch's
warehouse; the location is required, and may differ per package.

Each package receives its own **unique barcode** (`Brūkšninis kodas`), rendered as
a scannable EAN-13 graphic on the label. The barcode identifies the **physical
package only** and encodes **no business data** (no supplier, delivery, resource,
date or batch) — the relationships provide the meaning.

When registering the next package of a batch, the form **preselects the location
of the most recently registered package** (`suggestedLocationId`, derived from the
persisted data, so it survives refreshes and works across workstations); the
worker may still change it. With no previous package, no location is preselected
(there is no arbitrary fallback).

## Documentary piece count

`Batch.documentPieces` is the **type-specific documentary piece count**. For a
**PIECE** batch it is the required aggregate count compared with the actual sum of
active item lines (e.g. actual 18, documented 20 → `−2 vnt.`); it drives the PIECE
comparison and the optional PIECE discrepancy. For a **WEIGHT** batch it remains
an optional documentary field accepted by the API for compatibility, but it is
**not** a physical receiving unit, does **not** replace the document weight, and
is no longer rendered or submitted by the UI. There is no per-package or
per-product piece allocation.

Derived values shown in the API/UI (never stored, never client-supplied):

- `bagCount` — number of **active** packages in the batch (voided ones excluded);
- `totalNetWeight` — sum of **active** package **net** weights (the **measured**
  quantity), serialised as a **decimal string**; voided packages are excluded;
  gross and tare are preserved per package for traceability;
- `difference` — `totalNetWeight − documentWeight` for a reconciled batch (same
  precision; a signed decimal string), or `null` before reconciliation (positive
  = physically received **more** than documented);
- `suggestedLocationId` — the location of the most recent package (batch detail
  only), used to preselect the next package's location.

Weights are persisted as PostgreSQL `numeric` (Prisma `Decimal`) and exchanged as
**strings**, so they never pass through JavaScript floating point. The documentary
weight is **never** written over the measured weight.

## Delivery code, batch code and package barcode

- **Delivery code** — `G<YY><MM>-<NN>`, e.g. `G2609-01`. Generated by the API
  (two-digit sequence within the calendar month, resetting each month, max `99`
  with `DELIVERY_CODE_EXHAUSTED` past that), unique via a database constraint with
  retry on conflict. It is the **human-facing** reference shown in the receiving
  UI and printed on labels, and encodes no business data.
- **Batch code** — `P<NN>`, e.g. `P01`. Compact and **local to its delivery** (the
  first batch in a delivery is `P01`, the second `P02`, ..., max `P99`; the sequence
  resets for each new delivery and never silently produces `P100` —
  `BATCH_CODE_EXHAUSTED` past `P99`). Generated by the API, unique per delivery via
  a database constraint on `(deliveryId, code)` with retry on conflict. It is
  **secondary** to the delivery code and is not printed on labels. The
  IncomingDelivery code is the **main human-facing receipt identifier**; together
  they read e.g. `G2610-01 / P01`.
- **Package barcode** — a 13-digit, **EAN-13-shaped** code (GS1 `20` restricted-
  circulation prefix + 10 random digits + a valid check digit). Generated by the
  API, unique via a database constraint with retry on conflict. It encodes no
  business data and is **not** copied to child packages (splitting is out of scope).

## Status

| Key | Lithuanian | Meaning |
|---|---|---|
| `PENDING` | Laukiama patvirtinimo | created; packages may still be added |
| `CONFIRMED` | Patvirtinta | formally confirmed (terminal) |

There is **no** `DISCREPANCY` batch status. A documentary/physical mismatch does
**not** block confirmation: the batch is `CONFIRMED` and the mismatch is recorded
as a separate, long-lived `ReceivingDiscrepancy` (see "Receiving discrepancy").
Packages may be added, corrected or voided **only** while `PENDING`; a `CONFIRMED`
batch is frozen.

## Reconciliation (formal confirmation)

Reconciliation is the documentary/financial act performed later by an `ADMIN`
(Eimantas), after the physical packages have been registered. It records the
accepted documentary values, confirms the batch and resolves/creates the internal
formal-document anchor **server-side** — the user never selects a `GoodsReceipt`
or `GoodsReceiptLine`. It creates **no** packages and no stock.

- **Confirmation is never blocked by a mismatch.** An exact match
  (`measuredWeight == documentWeight`) confirms directly with no discrepancy. A
  mismatch still confirms, but the client must explicitly send
  `acknowledgeDiscrepancy: true` (`DISCREPANCY_NOT_ACKNOWLEDGED` otherwise); the
  document weight is **not** required to be edited to match the physical weight.
- **Two separate quantities:** the **measured** quantity is always server-derived:
  WEIGHT uses `SUM(bags.netWeight)` over the batch's active packages; PIECE uses
  `SUM(BatchItem.quantity)` over the batch's active item lines. The
  **documentary** value is entered at confirmation and depends on the batch type:
  WEIGHT enters `documentWeight` (kg); PIECE enters one aggregate
  `documentPieces` (`vnt.`). They are never merged, and the signed
  `difference = measured − documented` (positive = physically received **more**
  than documented) is shown as-is (no tolerance). A WEIGHT batch may additionally
  carry an optional documentary piece count through the API for compatibility, but
  the UI no longer renders or submits it.
- **Acquisition value:** `acquisitionAmount` (EUR) is stored on the batch as its
  **initial acquisition value**.
- **Relationship:** `GoodsReceipt → GoodsReceiptLine → Batch → Bags`.
  `Batch.receiptLineId` is a nullable, **unique** foreign key, so one receipt line
  reconciles at most one batch and one batch is reconciled to at most one line; a
  receipt may still contain multiple lines/resources/batches. The relationship is
  internal plumbing; the client sends only formal data.
- **Internal anchor resolution (no technical selector):**
  `POST /batches/:id/reconcile` carries only formal data (`documentWeight`,
  `acquisitionAmount`, optional `documentPieces`, optional document date/number).
  The server resolves the `GoodsReceiptLine` anchor deterministically:
  1. reuse the line the batch is already linked to (retry — no duplicate);
  2. reuse an existing compatible, **unlinked** receipt line (same supplier via
     the receipt partner, resource and warehouse);
  3. otherwise create a `GoodsReceipt` with one line from the batch + formal data
     (unit `KG`, quantity = documentary weight, unit price = value ÷ weight).
  A reused line is never mutated; the accepted documentary values live on the
  batch. Retrying never duplicates a receipt or line.
- **Document metadata:** `documentDate`/`documentNumber` live on the `GoodsReceipt`
  and may be supplied at reconciliation when not already set; an existing value is
  never overwritten.
- **Transactional & idempotent:** the confirm update and the discrepancy creation
  happen in one transaction; the batch update is conditional on not being
  `CONFIRMED`, so a retry (or concurrent confirmation) cannot create a duplicate
  discrepancy.

## Receipt-level transport and customs expenses (`Priėmimo išlaidos`)

Transport and customs are entered **once per `Priėmimas`**, not per batch. The
one `IncomingDeliveryExpense` row is shared by every `PXX` batch of the delivery,
so opening it from `P01` or `P02` reaches the same saved record. The amounts are
stored separately (`transportAmount`, `customsAmount`, both EUR, non-negative,
at most two decimals) and are **not** a supplier invoice, purchase price or
accounting entry.

### Allocation methods

| Method | UI label | Basis |
|---|---|---|
| `BY_VALUE` | `Pagal vertę` | all-WEIGHT receipt: each eligible batch's share of **actual net kg** (`Pagal partijų neto svorį.`); all-PIECE receipt: each batch's share of **actual pieces** (`Pagal priimtą vienetų kiekį.`); mixed WEIGHT + PIECE receipt: each batch's share of its **recorded acquisition amount in EUR**, excluding transport and customs (`Pagal partijų įsigijimo vertę eurais.`) |
| `EQUAL` | `Po lygiai` | equal share for every eligible batch |

- **Eligible** means the batch has a positive actual quantity (active package net
  weight or active item pieces). Zero-quantity batches receive no share.
- A **mixed** receipt can use `BY_VALUE` only when **every** eligible batch has a
  recorded acquisition amount and their sum is positive. A recorded `0,00 €` is a
  valid zero share. A missing value is unknown: the preview names the batch
  (`Trūksta įsigijimo vertės: P02.`), keeps `Po lygiai` available and blocks apply
  with `ACQUISITION_BASIS_UNAVAILABLE`. If every value is zero, the preview
  explains `Įsigijimo verčių suma lygi 0, todėl proporcinis paskirstymas
  negalimas.`; `EQUAL` remains available. There is no kg + vnt. denominator.
- The basis shown beside the method is derived from the eligible batches, so it
  still describes the eligible set rather than the whole receipt.
- Transport and customs are allocated **separately**, each to the cent, using
  largest-remainder rounding, so the shares always sum exactly to the entered
  amount. Example: 80 € transport and 20 € customs over 10 kg and 30 kg produce
  `20 € + 5 €` for `P01` and `60 € + 15 €` for `P02` under `BY_VALUE`; `EQUAL`
  produces `40 € + 10 €` for each. A mixed receipt with acquisition values
  `P01 = 6 000 €` and `P02 = 4 000 €` splits 2 000 € transport and 350 € customs
  as `1 200 € + 210 €` (60 %) and `800 € + 140 €` (40 %).

### Preview, apply and late invoices

- The manager screen shows one `Priėmimo išlaidos` block below the batch table.
  The proposed transport/customs share for every batch is previewed before apply.
- `POST /deliveries/:id/expenses/preview` computes the proposal without writing;
  `POST /deliveries/:id/expenses/apply` applies it to the **whole receipt**, and
  `PUT /deliveries/:id/expenses` remains a draft header save. All three are
  `ADMIN`-only, together with the `GET`.
- Applying writes one `DeliveryExpenseApplication` with the receipt amounts/method,
  `appliedById`, `appliedAt` and one `DeliveryExpenseApplicationEntry` per batch
  carrying the **previous** and **new** transport/customs shares.
- The batch's `allocatedTransportAmount`/`allocatedCustomsAmount` are the
  **current applied shares**. Stock valuation adds them once for each
  `CONFIRMED` batch. A pending batch contributes its share only when confirmed.
- A **late invoice or revised amount** can be applied after confirmation. A
  confirmed batch's physical quantity, confirmation, barcodes and discrepancy
  history are untouched; only its valuation changes by the share difference.
  Example: two 10 kg batches, P01 confirmed first, then a 100 € transport invoice
  is applied → P01 and P02 each get 50 €; P01's confirmed stock value rises by
  50 € immediately. Confirming P02 recognises its remaining 50 €. Revising the
  invoice to 120 € adds a further 10 € to each, leaving 0 € unallocated.
- Applying identical amounts/method again writes **no** application row and has no
  additional valuation effect.
- A receipt may be partially confirmed: only confirmed batches' current shares
  enter the dashboard; pending siblings do not.
- Receipts that never had expenses behave as zero: `GET` returns `0` / `0` with
  `updatedAt: null`; batches keep `null` allocations until an allocation is
  applied, and valuation uses only `acquisitionAmount`.

| Capability | Endpoint | Requirement |
|---|---|---|
| Read the shared receipt expenses | `GET /deliveries/:id/expenses` | `ADMIN` |
| Save a draft expense header | `PUT /deliveries/:id/expenses` | `ADMIN` |
| Preview the receipt allocation | `POST /deliveries/:id/expenses/preview` | `ADMIN` |
| Apply/reapply the receipt allocation | `POST /deliveries/:id/expenses/apply` | `ADMIN` |
| Delete a batch-less receipt (non-zero expenses block it) | `DELETE /deliveries/:id` | `ADMIN` or `WAREHOUSE_WORKER` |

`DELETE /deliveries/:id` locks the delivery row `FOR UPDATE`, counts its batches
and inspects the expense record in the same transaction. A receipt with any batch
is rejected with `DELIVERY_HAS_BATCHES`; a non-zero transport or customs amount is
rejected with `DELIVERY_HAS_EXPENSES`; a zero-amount expense record does not block
deletion and is removed by the cascade. The row lock prevents a concurrent
first-batch insert from slipping between the count and the delete.

## Receiving discrepancy (neatitikimas)

When a batch is confirmed with a non-zero `measuredWeight − documentWeight`, the
server records a `ReceivingDiscrepancy` (created by
`POST /batches/:id/reconcile` with `acknowledgeDiscrepancy: true`):

- `batchId` (**unique** — one discrepancy per confirmed batch), `supplierId`
  (snapshot from the delivery), `measuredWeight`, `documentWeight`,
  `differenceWeight` (signed `measured − document`), `status`, `createdById`,
  `createdAt`, `settledAt?`.

The discrepancy lifecycle is **separate** from the confirmation lifecycle:

- the batch is already `CONFIRMED`; the physical stock remains the measured net
  weight (gross/tare preserved per package);
- the discrepancy may stay **open for a long time**;
- it is settled later **by additional physical weight or by money/credit** through
  the append-only `DiscrepancySettlement` ledger (`WEIGHT`/`MONEY`); **no
  money↔weight conversion is ever performed**. Statuses:
  `OPEN | PARTIALLY_SETTLED | SETTLED`, with `settledAt` set once fully covered.

In the `Priėmimas` list a confirmed batch with an unresolved discrepancy is shown as
`Patvirtinta` with a `Neatitikimas` marker (it is **not** under `Reikia
patvirtinti`); the ADMIN detail shows the signed difference and the batch's
discrepancy records.

The discrepancy register and its settlement ledger are documented in full in
[discrepancies.md](discrepancies.md) (ADMIN `Ataskaitos → Neatitikimai`).

## Physical correction and voiding (worker)

Physical reality is authoritative. A warehouse worker may correct what they
physically measure/place without an ADMIN, while the batch is not yet `CONFIRMED`:

- **Correct a package** (`PATCH /batches/:id/bags/:bagId`): change
  `packagingTypeId`, `grossWeight` and/or `warehouseLocationId` on an **active**
  package. At least one field is required; the package must still be `ACTIVE` and
  the batch not `CONFIRMED`. A changed packaging type re-snapshots
  `Bag.tareWeightKg` from the selected type; a changed packaging type or gross
  weight recomputes `netWeight` server-side (`grossWeight − tareWeightKg`). The new
  location must exist, be active and belong to the batch's warehouse. Only the
  **changes** are recorded, one `BagCorrection` row per changed field
  (`PACKAGING` — with previous/new packaging name **and tare**, `GROSS_WEIGHT`,
  `LOCATION`); a no-op records nothing.
- **Void a package** (`POST /batches/:id/bags/:bagId/void`): the package is
  **never deleted**. It is marked `VOIDED` (who/when and optional reason) and
  excluded from the measured weight and active count; its barcode and history are
  preserved. A `VOID` row is appended to the trail.

The correction trail (`BatchDetail.corrections`, newest first) records the kind,
the affected package's barcode, previous/new value, reason, who and when.

| Code | HTTP | Meaning |
|---|---|---|
| `BAG_NOT_FOUND` | 404 | unknown package within the batch |
| `BATCH_CONFIRMED` | 409 | batch is `CONFIRMED` (frozen) |
| `BAG_VOIDED` | 400 | package is already `VOIDED` |
| `PACKAGING_INACTIVE` | 400 | selected packaging type is inactive |
| `GROSS_NOT_ABOVE_TARE` | 400 | gross weight is not greater than the tare |

- The batch detail page shows a **compact header** and a **read-only** list of the
  registered packages (`Barkodas`, `Vieta`, `Neto svoris`, `Būsena`,
  `Užregistruota`) with an optional label preview/reprint; voided packages are
  shown muted. The receipt and batch code are shown **once** as
  `Priėmimas GYYMM-NN / PXX`; the status, arrival date, supplier, resource,
  warehouse and actual quantity follow as one wrapping row (a second line is
  allowed on narrow screens), and the actions `Priėmimo GYYMM-NN išlaidos` and
  `Redaguoti partiją` (PENDING only) sit beside the heading. It also
  shows the **`Pataisymų istorija`** (correction history) table. There are **no**
  package-creation or correction controls here (those are worker actions).
- For a non-confirmed batch, `ADMIN` sees a **type-specific confirmation form**
  with formal data only:
  - WEIGHT: `Dokumentinis svoris, kg`, `Įsigijimo vertė`, `Dokumento data`,
    `Dokumento Nr.`; the summary is `Faktiškai susverta` / `Dokumentuose` /
    `Skirtumas` in kg.
  - PIECE: a documentary-form selector `Pagal prekes` / `Bendras kiekis`.
    Itemised mode shows `Prekė | Faktiškai | Dokumentuose | Skirtumas` with one
    input per product; total mode shows `Faktiškai užregistruota` and one
    `Dokumentinis kiekis, vnt.` field. Both share `Įsigijimo vertė`,
    `Dokumento data`, `Dokumento Nr.` and the `Faktiškai gauta` / `Dokumentuose` /
    `Skirtumas` comparison in `vnt.` Itemised is the default for a multi-product
    batch, total for a single-product batch; a confirmed itemised batch keeps its
    per-product table read-only.
  The applicable quantity field is chosen from the stored `receivingMode`, so it
  is correct even before any unit is registered. An empty documentary field shows
  `—` in the comparison; a non-zero difference is confirmed through the existing
  acknowledgement dialog and recorded as a `ReceivingDiscrepancy`. Switching
  batches clears the previous draft values. A `CONFIRMED` batch shows a read-only
  summary. The detail page's back link returns to the `Priėmimas` list
  (`/receipts`).

### Editing a PENDING batch

The batch detail page (`/receipts/batches/[id]`) shows **`Redaguoti partiją`** beside
the heading while the batch is `PENDING`. It opens the existing registration
interface at `/receiving/[deliveryId]/batches/[batchId]`, prefilled from the saved
receipt/batch/packages/items. No new delivery or batch is created; IDs, codes and
handling-unit barcodes stay stable.

- **Receipt scope:** supplier and arrival date belong to the whole delivery. They
  are labelled as such and are editable only while **no sibling batch in the
  delivery is confirmed**. If one is confirmed, the API rejects those fields with
  `DELIVERY_HAS_CONFIRMED_BATCHES`; batch-only fields remain editable.
- **Batch scope:** WEIGHT has one batch resource; PIECE has per-line resources.
  Warehouse changes are allowed; when active bags/items exist, a target location
  of the new warehouse is required and all active units are relocated (bag
  `LOCATION` corrections are recorded; barcodes unchanged).
- **Units:** existing add/correct/void operations are reused. Bag corrections
  cover packaging/tare, gross weight, location and void; PIECE item corrections
  cover resource, quantity, location and void.
- **Save/cancel:** `Išsaugoti pakeitimus` writes receipt/batch metadata and returns
  to the same batch detail; `Atšaukti` discards the unsaved metadata form. Unit
  operations have their own immediate save/cancel. Saving never changes
  `PENDING`; the code-labelled per-batch confirmation (`Patvirtinti PXX`) on the
  manager receipt screen remains a separate ADMIN action.
- **Concurrency:** all registration/content mutations lock the batch row (and all
  delivery rows for shared receipt fields) and re-check `PENDING`. An edit that
  arrives after confirmation is rejected with `BATCH_CONFIRMED` and no data is
  written; the UI refreshes the status.
- **Validation:** existing server rules remain authoritative (active
  resource/warehouse/packaging/location, location belongs to warehouse, gross
  above tare, positive integer piece quantity). Lithuanian field messages are
  shown in the UI.
- **List continuity:** `/receipts` persists its filters in `sessionStorage`
  (`aitvaras.priemimas.filters.v1`), so returning from a detail/edit restores the
  same queue view.

API: `PATCH /batches/:id/registration` (`ADMIN` / `WAREHOUSE_WORKER`), contract
`UpdateBatchRegistrationRequest`. `PATCH /batches/:id/items/:itemId` now accepts
`resourceId` for PENDING PIECE lines.

### Warehouse-worker receiving UI (`Priėmimas`)

The warehouse worker's job is the **physical** receiving step only; the formal
`Pajamavimas` process is administrative and is not part of their flow.

- **Home** (`/`): for a receiving role the home is a focused operational
  workplace whose primary action is the prominent `Naujas priėmimas` button.
- **Receipt list** (`/receipts`, protected by the receiving roles): the single
  `Priėmimai` list, **one row per receipt** even when it contains several batches.
  Columns: `Priėmimas`, `Priėmimo data`, `Tiekėjas`, `Patvirtintos partijos`,
  `Būsena`, `Veiksmai`.
  - `Laukia patvirtinimo` (default) shows receipts with at least one pending
    batch, including partially confirmed receipts; `Patvirtinta` shows receipts
    whose batches are all confirmed; `Visos` also adds zero-batch receipts.
  - `Patvirtintos partijos` is `—` for zero batches, otherwise `confirmed iš total`.
    Statuses: `Be partijų`, `Laukia patvirtinimo`, `Patvirtintas`.
  - Supplier/date filters apply at receipt level. Resource/warehouse/batch-code
    filters match a receipt **once** when any of its batches matches all supplied
    batch-specific filters; zero-batch receipts cannot match them.
  - Rows are grouped first, then sorted newest-first and paginated (`20` per page).
  - The G… code opens the operational receipt page `/receiving/[deliveryId]` for
    every status and every receiving role. `Tvirtinti` (pending, confirmation
    permission) and `Peržiūrėti` (fully confirmed, manager access) open the
    manager screen `/receipts/[deliveryId]`.
  - `Atstatyti filtrus` returns to `Laukia patvirtinimo` (zero-batch receipts are
    hidden).
  - A zero-batch row offers **`Ištrinti priėmimą`** when the receipt has no
    non-zero recorded expense. Deletion asks `Ištrinti priėmimą GYYMM-NN?` with
    `Atšaukti` / `Ištrinti`, then refreshes the list, keeps the filters and reports
    through the global toast. A non-zero expense shows
    `Negalima ištrinti: užregistruota transporto arba muitinės išlaidų.` instead.
  - The old `/receiving` index is a redirect to `/receipts`.

### Manager receipt screen (`/receipts/[deliveryId]`, ADMIN)

One confirmation screen per receipt: `Priėmimas G…` heading, supplier/arrival once,
then one bordered group per batch with `Partija`, `Prekė`, `Priimta`,
`Dokumentuose`, `Skirtumas`, `Įsigijimo vertė, €` and `Būsena / veiksmas`.
Expanding a group keeps its summary row, document fields, product table and
confirmation action inside the same continuous border, with a muted background and
a `PXX prekės` product heading; the next batch starts outside that border.

- A single toggle sits directly below the product in the `Prekė` column and uses
  the same compact outlined style, chevron, pointer cursor and
  `focus-visible` ring. Multi-product PIECE batches label it
  `Rodyti prekes` / `Slėpti prekes`; WEIGHT and single-product batches label it
  `Dokumento duomenys` / `Slėpti detales`. Both open the same panel, so a batch
  never shows two expansion controls.
- Collapsed summary columns stay aligned with their headings across every batch.
  `Būsena / veiksmas` contains only the status or the collapsed
  `Patvirtinti PXX` action.
- `Priimta` is read-only from active packages (`netWeight` kg for WEIGHT) or active
  item lines (`vnt.` for PIECE), including zero.
- `Dokumentuose` accepts the matching unit; `—` is shown for an empty difference.
- When a pending batch is expanded, every empty/invalid **required** input gets a
  red border immediately and carries `aria-required` plus `aria-invalid`. The
  border clears as soon as the value satisfies the same rule as confirmation and
  returns if it is cleared again:
  - WEIGHT: `Dokumentinis svoris, kg` (positive) and `Įsigijimo vertė` (a recorded
    `0` is valid);
  - PIECE `Pagal prekes`: each product's `Dokumentuose` value independently (a
    whole number, `0` included);
  - PIECE `Bendras kiekis`: the single total instead.
  Optional `Dokumento data` and `Dokumento Nr.` stay neutral.
- A multi-product PIECE batch shows `N prekės`; expanding it reveals the
  `PXX prekės` product table and the existing itemised comparison, with
  `Pagal prekes` / `Bendras kiekis` preserved so itemised shortages and surpluses
  are recorded separately.
- Document date/number and the discrepancy acknowledgement are available in the
  expanded row / confirmation dialog.
- Each pending batch has exactly one confirmation button carrying its code:
  `Patvirtinti P01` sits on the collapsed summary row and moves to the
  bottom-right of the group, immediately after the expanded inputs. The
  discrepancy dialog names the same batch (`Patvirtinti P01 su neatitikimu?`).
  Confirmation applies only to that batch; the receipt list derives
  `Patvirtintas` when the last batch is confirmed. There is no separate
  receipt-confirmation button.
- The `Priėmimo išlaidos` block sits below the batch groups and is manager-only.
  The proposal preview shows each batch's `Įsigijimo vertė, €` beside its actual
  quantity so a mixed `Pagal vertę` split can be checked before apply.
- Warehouse workers do not see this screen or any acquisition/transport/customs
  controls; they retain the operational `/receiving/...` screens, direct links and
  pending-batch continuation.
- **New receipt** (`/receiving/new`): only the receipt header form
  (**`Tiekėjas`** + **`Atvykimo data`**; no warehouse, no resource; the code is
  system-generated). Opening or leaving this form creates **no database record**;
  `Pradėti priėmimą` is the explicit `POST /deliveries` that creates the receipt
  and opens `/receiving/[deliveryId]`.
- **Delivery screen** (`/receiving/[deliveryId]`): opening a started/selected
  receipt or creating one navigates to its own route, so the URL is
  bookmarkable/refreshable and browser Back works naturally; the page heading
  `Priėmimas <code>` is shown **once**, the `Priėmimo turinys` heading sits above
  its batch table, and `← Priėmimų sąrašas` returns to `/receipts`. The top-level
  `Priėmimas` navigation stays active throughout. The screen is **delivery
  first**: supplier and arrival date, the batch table, then the `Nauja partija`
  resource/warehouse selection. The worker uses **`Pradėti registruoti`** to start
  or resolve one batch per resource/warehouse; **`Kitas išteklius`** clears the
  active resource/batch and starts another batch **in the same delivery**
  (packaging preference is batch-specific — a new batch starts without a `Tara`
  selection). When **every** batch of the receipt is `CONFIRMED`, the operational
  screen becomes read-only: the `Nauja partija` block is replaced by
  `Priėmimas patvirtintas. Duomenų keisti negalima; …`, rows still open the batch
  contents and label reprinting for active units, and receipt-level expense
  revisions stay on the manager screen. A partially confirmed receipt keeps the
  `Nauja partija` block and editable pending batches; each `CONFIRMED` row opens
  read-only. Direct URLs to a confirmed batch produce the same read-only view, and
  the server still rejects physical changes (`BATCH_ALREADY_CONFIRMED`). Package entry
  takes **`Tara`** (active packaging types only), **`Vieta`** (required) and
  **`Bruto svoris`**; the UI shows the calculated **`Taros svoris`** and **`Neto
  svoris`** (the worker enters only the gross weight). The batch's **latest active
  package** supplies the suggested packaging type (`suggestedPackagingTypeId`) and
  location (`suggestedLocationId`) — server-derived so they survive a
  refresh/re-entry; a batch with no active package suggests nothing.
- **Batch editor** (`/receiving/[deliveryId]/batches/[batchId]`): the
  `Priėmimo turinys` heading stays above the batch table, and the navigation
  action to the parent receipt is labelled `Redaguoti priėmimą` while the batch is
  `PENDING` and the operator may edit, otherwise `Peržiūrėti priėmimą`. It opens
  `/receiving/[deliveryId]` for that exact batch's parent receipt. A
  `CONFIRMED` batch, whether reached from the receipt table or a direct URL,
  shows no add/correct/void or `Redaguoti partiją`/`Nauja pakuotė` controls;
  active packages remain visible with `Spausdinti` for label reprinting. Receipt
  transport/customs revision stays available to ADMIN through
  `/receipts/[deliveryId]`.
- **Save actions:** **`Išsaugoti ir spausdinti`** (primary — persists the package
  and goes **straight to the label surface**, invoking the browser print preview)
  and **`Išsaugoti`** (secondary — persists and returns to the form). Both keep the
  active resource/batch, the selected `Tara` and the last-used location
  (server-derived suggestions) and reset **only the gross weight**; closing the
  label returns to the same form. A failed save opens no label and keeps the
  entered data.
- **Package list:** below the entry form, the active batch's **active** packages
  are listed under `Partijos pakuotės`, newest first, with `Barkodas`, `Vieta`,
  `Neto svoris`, `Užregistruota` and row actions `Taisyti`, `Anuliuoti` and
  `Spausdinti` (reprint). Voided packages move to `Anuliuotos pakuotės`. Correcting
  a package opens an editor with `Tara`, `Vieta`, `Bruto svoris` and the computed
  tare/net.
- **Label:** `Priėmimas: GYYMM-NN` (prominent), warehouse, location, category,
  resource, **`Neto svoris`** (primary; gross/tare shown as secondary
  traceability), and the barcode (value + scannable EAN-13 graphic). The internal
  batch code is not printed.
- **Navigation**: the worker navigates `Suvestinė`, `Priėmimas`, reference data
  under the `Žinynai` group (`Partneriai`, `Ištekliai`, `Sandėliai`); the
  administrative `Ataskaitos`/`Nustatymai` groups are hidden. `ADMIN` keeps full
  access. Server-side authorization is unchanged.

### Server-side validation (authoritative)

The API verifies (never trusting UI filtering):

- on delivery creation: the supplier exists, is active and holds the `SUPPLIER`
  role;
- on batch resolution: the delivery exists, and the resource and warehouse exist
  and are active;
- a package's `grossWeight` > 0, the selected packaging type exists and is active
  (`PACKAGING_INACTIVE` otherwise), and `grossWeight > tareWeightKg`
  (`GROSS_NOT_ABOVE_TARE` otherwise); the net weight is computed server-side and
  never trusted from the client;
- a package's **location is required** and must exist, be active and belong to the
  **batch's** warehouse (friendly message: `Pasirinkite sandėlio vietą.`);
- packages can be added or corrected **only** while the batch is `PENDING` (a
  `CONFIRMED` batch is frozen — `BATCH_CONFIRMED`); a corrected package must be
  `ACTIVE` (`BAG_VOIDED` otherwise);
- reconciliation requires a non-empty batch, a non-`CONFIRMED` batch, a compatible
  receipt line, `documentWeight > 0`, an optional positive-integer
  `documentPieces`, a non-negative acquisition amount, and — when the measured net
  weight differs from `documentWeight` — `acknowledgeDiscrepancy: true`; the
  measured weight and the signed difference are computed server-side and never
  trusted from the client.

## Referential behaviour

Deliveries reference `BusinessPartner` and `User`; batches reference
`IncomingDelivery`, `Resource`, `Warehouse`, `User` and (optionally) a
`GoodsReceiptLine`; packages reference `Batch`, `PackagingType`,
`WarehouseLocation` and `User`; `BagCorrection` rows reference `Bag` and `User`.
Referenced master data is
deactivated, never deleted, and foreign keys **restrict** deletion. There is no
delivery/batch/package delete endpoint — a package is **voided**, never deleted.

## Migration notes (historical data)

The `incoming_deliveries` migration (ATV-042) created **one delivery per existing
batch**, because the real shared arrivals of the past cannot be proven from stored
data. Each migrated delivery reuses its batch's id, copies the supplier + arrival
date and receives a deterministic per-month `GYYMM-NN` code; the batch **keeps its
warehouse**. Existing packages were preserved: `bags.quantity` was renamed to
`bags.weight` (the KG/PCS unit column was dropped) and `batches.document_pieces`
was added. Do not infer historical delivery grouping.

The `packaging_types` migration (ATV-043, extended by ATV-044) introduced
`PackagingType` and gross/net weights plus the `Bag.tareWeightKg` snapshot.
Existing handling units had **no known packaging/tare provenance**, so they were
attached to a dedicated, **inactive** `Nežinoma tara` row with tare `0.000`; their
tare **snapshot** is `0.000`, `grossWeight` was set equal to the stored weight and
`netWeight = grossWeight` is preserved unchanged (no invented tare). The inactive
row cannot be chosen for new receiving. New packages snapshot the selected
PackagingType's current tare.

The `batch_delivery_local_code` migration (ATV-047) shortened the human-facing
batch code to the delivery-local `P01`..`P99` and replaced the global unique
`batches.code` index with a composite unique index on `(deliveryId, code)`.
Existing batches were renumbered deterministically within each delivery (`P01`,
`P02`, ... by creation order, relationships preserved). **Limitation:** a delivery
with more than 99 historical batches would produce `P100+`; this cannot occur with
the current data (each migrated delivery holds a single batch) and new batches are
capped at `P99`.

## Open / not implemented

- **Vehicle/transport** — explicitly **outside system scope** (not modelled).
- **Historical delivery grouping** — migrated deliveries are one-per-batch.
- **Bag split / merge and EAN lineage to child packages** — not modelled.
- **Post-confirmation corrections** — a `CONFIRMED` batch is frozen.
- **Piece allocation per package** — not modelled; pieces are documentary only.
- **Packaging-type deletion** — never hard-deleted; deactivated only
  (`docs/packaging-types.md`).
- **Tolerance percentages** — exact equality is the only clean-confirmation rule.
- **`Bag`/`Maišas` naming** — the internal model is still called `Bag`; renaming
  it to `HandlingUnit` is a deferred, purely mechanical refactor.
- **VAT/accounting engine, cost redistribution, production transformations,
  output lots, order allocation** — confirmed future direction, not modelled here.
