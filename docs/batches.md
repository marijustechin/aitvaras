# Batches and Bags (Partijos ir maišai)

> Status: **implemented (first iteration)** — task ATV-029. Incoming **batch/lot**
> registration with individual physical **bags/handling units** and a unique
> barcode. This is the first slice of the confirmed inventory/production
> direction (see [scope.md](scope.md)); it deliberately does **not** implement
> stock balances, movements, production lineage or costing.

## What a Partija is (and is not)

A **Partija** (batch/lot) records one physical delivery of **one** resource from
**one** supplier into **one** warehouse. It is created at the start of bag-by-bag
registration and stays **`PENDING`** until a responsible person confirms it.

It is deliberately **independent of** the formal `Pajamavimas` (GoodsReceipt). A
batch can later be reconciled with a receipt **without duplicating quantities**:
the receipt remains the transactional record; the batch/bags carry physical
traceability. The structural link between a batch and a receipt is **intended but
not yet modelled** (see "Open / not implemented").

A Partija is **not** stock: creating a batch or a bag does **not** change any
balance, and there is no quantity-on-hand anywhere in the system.

## What a Maišas (bag / handling unit) is

A **Maišas** is one physical handling unit inside exactly one batch. Incoming raw
material usually arrives as many bags of one batch, and **bags of the same batch
may have different actual weights** — the weight is measured per bag.

Each bag receives its own **unique barcode** (`Brūkšninis kodas`). The barcode
identifies the **physical unit only** and encodes **no business data** (no
supplier, resource, date, batch or cost) — the relationships provide the meaning.
Bags are not deleted; there is no bag edit/delete endpoint.

## Domain model

```text
Batch
├── id
├── code                (unique, human-readable, system-generated)
├── resourceId          (Išteklius)
├── supplierId          (Tiekėjas — active SUPPLIER partner)
├── warehouseId         (Sandėlis)
├── arrivalDate         (physical arrival; independent of createdAt)
├── status              PENDING | CONFIRMED | DISCREPANCY  (default PENDING)
├── createdById
├── createdAt / updatedAt
└── bags[]              (derived totals only — not stored)

Bag
├── id
├── barcode             (unique; physical unit identifier)
├── batchId
├── weight              Decimal(14,3), measured per bag, > 0
├── warehouseLocationId (optional; must belong to the batch's warehouse)
├── createdById
└── createdAt / updatedAt
```

Derived values shown in the API/UI (never stored, never client-supplied):

- `bagCount` — number of bags in the batch;
- `totalWeight` — sum of bag weights, serialised as a **decimal string**.

Weights are persisted as PostgreSQL `numeric` (Prisma `Decimal`) and exchanged
as **strings**, so they never pass through JavaScript floating point.

## Batch code and bag barcode

- **Batch code** — `P-<year>-<6-digit sequence>`, e.g. `P-2026-000042`.
  Generated by the API (sequential per calendar year), unique via a database
  constraint with retry on conflict. Human-readable for labels and reports.
- **Bag barcode** — a 13-digit, **EAN-13-shaped** code (GS1 `20` restricted-
  circulation prefix + 10 random digits + a valid check digit). Generated by the
  API, unique via a database constraint with retry on conflict. It encodes no
  business data and is **not** copied to child units (splitting is out of scope).

## Status

| Key | Lithuanian | Meaning |
|---|---|---|
| `PENDING` | Laukiama patvirtinimo | created; bags may still be added (functional now) |
| `CONFIRMED` | Patvirtinta | confirmed (reserved for the future confirmation step) |
| `DISCREPANCY` | Neatitikimas | discrepancy found (reserved) |

Only `PENDING` is functional in this slice: new bags may be added **only** while a
batch is pending. The confirmation UI/flow that moves a batch to `CONFIRMED`/
`DISCREPANCY` is **not implemented**; `CONFIRMED`/`DISCREPANCY` exist structurally
so the status concept is stable in data.

## API, contracts and UI

- API module: `apps/api/src/modules/batches/` (controllers, service, mapper,
  code/barcode generation).
- Shared contracts: `@aitvaras/contracts` (`batches.ts`).

| Capability | Endpoint | Requirement |
|---|---|---|
| List batches (optional `?status=`) | `GET /batches` | authenticated |
| Batch detail (with bags) | `GET /batches/:id` | authenticated |
| Start a batch | `POST /batches` | `ADMIN` or `WAREHOUSE_WORKER` |
| List a batch's bags | `GET /batches/:id/bags` | authenticated |
| Add a bag | `POST /batches/:id/bags` | `ADMIN` or `WAREHOUSE_WORKER` |
| Look up a bag by barcode | `GET /bags/by-barcode/:barcode` | authenticated |

- UI routes (inside the shell): `/receipts/batches` (start a batch + list) and
  `/receipts/batches/[id]` (detail, add bags, label preview/print). Reached from
  the `Pajamavimas` page (`Partijos →`).
- The batch detail page shows each bag's barcode and offers a **label preview**
  (resource name, `Partija`, weight, arrival date, barcode value) with a print
  action (`window.print()`). A rendered scannable barcode **graphic** is not
  implemented yet — the barcode is shown as text (see follow-ups).
- Creating a batch/add-bag form is shown only to `ADMIN`/`WAREHOUSE_WORKER`; the
  server remains authoritative regardless of UI visibility.

### Server-side validation (authoritative)

The API verifies (never trusting UI filtering):

- the resource exists and is active;
- the supplier exists, is active and holds the `SUPPLIER` role;
- the warehouse exists and is active;
- bag `weight` > 0 (decimal);
- a bag's location, **when supplied**, exists, is active and belongs to the
  batch's warehouse;
- bags can be added **only** to a `PENDING` batch.

## Referential behaviour

Batches reference `Resource`, `BusinessPartner`, `Warehouse` and `User` by id;
bags reference `Batch`, `WarehouseLocation?` and `User`. Referenced master data is
deactivated, never deleted, and foreign keys **restrict** deletion, so historical
batches/bags keep valid references. There is no batch/bag delete endpoint.

## Open / not implemented

- **Batch ↔ receipt link.** The intended model is `Receipt ↔ Batch → Bags` with no
  quantity duplication, but no `receiptId`/`batchId` FK exists yet. Adding it is a
  deliberate follow-up, not inferred here.
- **Confirmation/reconciliation** (`PENDING → CONFIRMED/DISCREPANCY`), document vs
  measured weight, and any discrepancy handling.
- **Scannable barcode graphic** on labels (currently the value is printed as text).
- **Splitting/merging** handling units and EAN lineage to child units.
- **Production lineage and batch/output-lot costing** — confirmed future
  direction, not modelled here (see [scope.md](scope.md)).
